### 0.2 ポートの分離（userData 分離だけでは解決しない）

**問題**: `main.js:13` の `HOOK_PORT = 47832` は固定値。`main.js:199-203` は EADDRINUSE をログ出力で握りつぶす。さらにフックスクリプトは**ポートを埋め込んだ状態で各プロジェクトに書き込まれる**（`main.js:431`）。

結果、開発版と常用版を同時起動すると後発はポートを取れず、**全プロジェクトのフック通知が先に起動した方に届く**。`--user-data-dir` では一切解決しない。MCP サーバを足すと同じ問題がもう1つ増える。

- [ ] ポートを固定値からプロファイル別に切り替え可能にする（開発版は別ポート）
- [ ] EADDRINUSE を握りつぶさず、別ポートへのフォールバックか明示エラーにする
- [ ] 実ポートをディスカバリ可能にする（`userData` 配下にポートファイルを書き出し、フックスクリプトが読む）
  - これがないと、フックスクリプトの埋め込みポートが常に古くなる
- [ ] MCP サーバのポートも同じ機構に載せる

### 0.3 ビルドシステムの導入（Phase 1 以降の前提条件）

**問題**: 現状は `index.html:105-109` の `<script src>` 直書きでバンドラなし。`main.js:48` が `loadFile` のため origin は `file://`。

- `<script type="module">` は file:// origin では CORS でブロックされる → Phase 1 の `src/commands/*.js` 分割が成立しない
- **CodeMirror 6 は ESM のみで UMD ビルドを提供していない**
- Vue 3 の SFC も同様

- [ ] esbuild を導入（vite でもよいが、Electron の file:// ロードに対しては esbuild の単純バンドルで足りる）
- [ ] `renderer.js` を単一バンドル出力に切り替え（この時点では中身を分割しなくてよい。経路だけ通す）
- [ ] `npm run build` / watch モードを `npm run dev:v2` に組み込む
- [ ] `package.json:31-38` の electron-builder `files` をバンドル出力に合わせて更新
- [ ] CSP（`index.html:5`）が `script-src 'self'` のまま通ることを確認

### 0.4 フック書き込み先の修正（D16）

**問題**: `main.js:471` は `.claude/settings.json` に直接書き、`hooks.Notification` / `hooks.Stop` を丸ごと上書きする。`settings.json` をコミットして共有しているプロジェクトで差分を作る。「他人の仕組みを阻害しない」（D16）に反する。

**このインデックスは Phase 1 で再利用する。** `get_focus` の周辺情報、将来のクイックオープンの土台になるため、**v2 の「注意状態の state」の一部として設計しておく**（doc 12）。

## Phase 1: コマンド層の骨格 + `get_focus`（1〜2週間）

### 位置づけ

- **アーキテクチャの足場**として最優先（doc 13）
- 差別化としては JetBrains（2025.2 以降、全 IntelliJ 系に MCP サーバをバンドル・既定で有効）や VSCode 拡張群に削られる。**プロダクトの存在理由ではなく、コマンド層（D10）を実在させるための最初の1機能**
- 抽象的な枠から設計すると空回りするため、具体的な要求で骨格を引き出す

### スコープの絞り込み（重要）

doc 12 は「**3 まで来た時点で `get_focus` が実際に動く。4 は既存 UI を段階的に移せばよく、一度に全部やる必要はない**」と明示している。

1. 「人間の注意状態」を1箇所に集約する state
2. それを更新するコマンド（タブ切替・選択・フォーカス移動）
3. MCP サーバから読み出す経路
4. UI をその state に従属させる ← **段階的でよい。Phase 1 の完了条件に含めない**

`renderer.js` は 1645 行あり、全状態のコマンド化を Phase 1 に含めると終わらない。**`get_focus` が返す情報に必要な状態だけ**を対象にする。

### 1.1 コマンド層の定義（D10）

すべての UI 操作に名前を与え、単一のコマンド語彙を通す。

```
MCP (agent) ──┐
キーボード   ──┼→ Command層 → State → 描画
マウス/UI    ──┘
```

**規律**: 状態変更は必ずコマンド経由。ライブラリの選択ではなく規律が本体。

#### 初期コマンド語彙（`get_focus` 実装に必要な分のみ）

| コマンド | 引数 | 由来 | 用途 |
|---|---|---|---|
| `select_project` | `projectId` | マウス/キー/MCP | プロジェクト切替 |
| `open_file` | `path` | ツリーdblclick/MCP | ファイルをエディタで開く |
| `open_preview` | `path` | ツリーdblclick/MCP | ファイルをプレビューで開く |
| `close_tab` | `filePath` | 中クリック/MCP | タブを閉じる |
| `switch_tab` | `filePath` | タブクリック/MCP | タブ切替 |
| `focus_terminal` | `tabId` | タブクリック/MCP | ターミナルにフォーカス |
| `send_to_terminal` | `text, tabId?` | scratch送信/MCP | ターミナルへテキスト送信 |
| `get_focus` | なし | MCP専用 | 人間の注意状態を返す |

**設計原則**: 新機能は必ずコマンド定義を伴う。これにより「つぎはぎ」が構造的に起きない。

#### ファイル構成案

Phase 0.3 のバンドラ導入が前提。

```
src/
  commands/
    registry.js      # コマンド登録・ディスパッチ
    types.js         # コマンド定義（名前・引数・戻り値）
    handlers/
      project.js     # select_project 等
      editor.js      # open_file, close_tab 等
      terminal.js    # focus_terminal, send_to_terminal 等
      focus.js       # get_focus
  store/
    index.js         # 状態ストア（コマンド経由で更新）
  mcp/
    server.js        # MCP サーバ（main プロセス）
    tools.js         # MCP ツール定義（コマンド層のクライアント）
```

**ターミナル描画の境界を引く**（doc 12 の「設計上の備え」）: xterm.js を差し替え可能な形に閉じ込める（`create` / `write` / `resize` / `dispose` / `paste` 程度）。コマンド層を作るついでに引いておけば、将来の移行が局所化する。

### 1.3 `get_focus` MCP ツール実装（D13）

**人間が今見ているもの**をエージェントが問い合わせられるようにする。

#### 返す内容（暫定）

```json
{
  "project": {
    "id": "...",
    "name": "project-mixer",
    "path": "D:/work/project-mixer"
  },
  "editor": {
    "activeTab": "src/main.js",
    "filePath": "D:/work/project-mixer/src/main.js",
    "isPreview": false,
    "selection": { "startLine": 12, "endLine": 18 },
    "cursorLine": 15
  },
  "terminal": {
    "activeTabId": "...",
    "command": "claude"
  },
  "scratch": {
    "content": "src/main.js の15行目の...",
    "length": 120
  }
}
```

**`terminal.cwd` は含めない**（初版から削除）。ターミナル CWD の取得には OSC 7 が必要で、PowerShell は既定で出さないためプロンプト関数への注入が要る。doc 14 の訂正により「OSC 7 はパースが安いだけで発信側は OSC 133 と同じ問題を抱える」と判明しているため、Phase 1 のスコープから外す。プロジェクトルートで足りるかを実使用で確認し、足りなければ注入込みで別途見積もる。

**設計上の注意**:
- 単なる「現在のファイル」ではなく、**人間の注意状態**として設計する
- PM は 5〜10 プロジェクトを抱えるため「どのプロジェクトの」が付く（Copilot / VSCode 系より情報量が上回る唯一の点）
- 巨大な terminal log を自動注入しない
- **D11 の判定を通す**: 「これは Shared View に載るか（人間に見せるためか、エージェント自身の作業のためか）」

#### MCP サーバ実装 — transport は HTTP に確定

**stdio は成立しない。** Claude Code は MCP サーバを子プロセスとして spawn するため、spawn された新プロセスは**動いている PM の状態を持たない**。PM は常駐 GUI アプリなので、既に起動しているプロセスに接続する経路が必要。

採る方式:

- **(a) HTTP/SSE**（採用）: PM の main プロセスで常駐サーバを立て、`claude mcp add --transport http` で接続する。Phase 0.2 のポート機構にそのまま載る
- (b) stdio ブリッジ: 薄い中継プロセスを配って PM の HTTP に転送する。(a) が使えない環境が出た場合の代替として保持

実装:

- [ ] `@modelcontextprotocol/sdk` を main プロセスに追加
- [ ] MCP サーバを HTTP transport で起動（Phase 0.2 のポート機構を使用）
- [ ] `get_focus` ツール定義 → コマンド層経由で renderer から状態を収集
  - main → renderer へ `ipcMain.handle('get_focus')` で状態取得
  - renderer は store から現在の注意状態を構築して返す
- [ ] MCP ツール名は退屈にする（D11）。`get_focus` / `show_file` のように説明的に。Shared View は層の呼称でありツール名ではない

### 1.4 検証

- [ ] Claude Code から `get_focus` を呼んで、PM の注意状態が返ることを確認
- [ ] **開発版と常用版を同時起動した状態で、正しい方の注意状態が返ること**（Phase 0 の実効確認）

### 実装経路（doc 12 の訂正1）

初版 D14 の「WebContentsView に Playwright のブラウザを埋め込める」は**誤り**。WebContentsView は Electron 自身のコンテンツ用で、外部プロセスのウィンドウは取り込めない。

- **経路1: CDP screencast** — Playwright のブラウザに CDP で接続しフレームを受け取って描画。表示専用で D15 と完全に整合
- **経路2（推奨）: PM がブラウザ面を提供し、エージェントが接続する** — PM が WebContentsView を出し remote debugging を有効化。Playwright は Electron を `--remote-debugging-port` 付きで起動して内部 Chromium に CDP 接続できる

経路2 なら D14（Electron 維持）の論拠が「WebContentsView に埋め込めるから」ではなく **「Electron の面が Chromium なので Playwright が CDP で掴めるから」** に変わり、むしろ強くなる。

## 保留・後回し

### OSC 133 / ターミナル意味情報 — **保留（実装しない）**

doc 14「結論の更新」で取り下げ済み。11節の P0〜P3 は当面実行しない。

**理由**: OSC 133 が刻むのは**コマンドの境界**だが、実用途は「`npm run dev` を起動したまま、操作後に出たエラー」であり、**コマンドブロックは1つのまま**で境界情報が生まれない。Claude Code / Codex のフルスクリーン TUI 実行中も「1コマンドが数時間続く」状態になる。効果範囲は shell タブの短命コマンドに限られ、実用途と噛み合わない。

代わりに **Phase 0.5.1「直近出力の送信」**（半日、OSC 133 の 1/20 以下の工数）を実装する。

**再浮上条件**: shell タブでの短命コマンド実行が実使用で増え、かつ「どのコマンドの出力か」の指定が摩擦になった場合。

### エージェント内部状態 — **公式フックから取る**

doc 14 の比較により、コスト順は 公式フック > セッション記録ファイル > MCP 観測 > ACP。用途（ターン終了検知・変更ファイル取得）は**公式フックで足りる**。PM は既にフック機構を持っている（`main.js:179-203`）。

ACP は監視項目にとどめる（クライアント化は D1・D2 の撤回を伴い、工数1ヶ月以上）。

### CodeMirror 6（D9）— 翻訳チャネルとセットで

D9 の条件成立理由は「**行を指差す行為＝空間的指示の翻訳が中核機能**」。だが**そのチャネル自体がまだ存在しない**。`show_file(path, line)` や「行選択→scratch 挿入」を伴わずにエディタだけ差し替えても、翻訳チャネルは1つも増えない。

**着手条件**: 行単位の指差しチャネル（`show_file` または行選択送信）を実装すると決めたとき。同じ Phase で扱う。

**歯止め（D9 のまま有効）**: `package.json` に以下が現れたら違反。grep で機械的に検出可能。
- `@codemirror/lang-*`
- `@codemirror/autocomplete`
- LSP 系パッケージ

**前提**: Phase 0.3 のバンドラ導入（CodeMirror 6 は ESM のみ）。

### Git 変更状態の簡易表示（D16）— 後回し

優先度低。変更ファイル一覧 + `git diff --stat` 相当のみ。差分ビューアは作らない。

着手時の非阻害ルール（D16）:
1. `git --no-optional-locks` を必ず付ける（`.git/index.lock` の奪い合いで相手のコミットを失敗させる）
2. Git hook を設置しない
3. `.git` の watch は `HEAD` と `index` だけ、200ms デバウンス。`.git/objects` は無視
4. worktree では `.git` がファイル。`git rev-parse --git-dir` で解決する

### Vue 3 移行（doc 12）— 時期未定

コマンド層が完成した後に検討。UI に残るのは描画とイベント発火だけになるため、選定軸は「摩擦が少なく、主役に出しゃばらないか」。

**選定理由（doc 12 の訂正を反映）**:

初版に書いた3根拠のうち2つは doc 12 の「訂正2」で無効になっている。

| 初版の根拠 | 現状 |
|---|---|
| `<KeepAlive>` が標準（ターミナルはアンマウントできない） | **誤り**。KeepAlive は DOM を隠しコンテナへ移すため xterm.js の寸法計測が 0 になる。正解は `display:none` + 再表示時 `fit()` で、**フレームワーク非依存** |
| xterm.js / CodeMirror 6 の非制御領域を作れる | 事実だが**フレームワーク非依存**。VDOM を持たない Solid が技術的には最良 |
| WebContentsView の矩形管理 | 同上。フレームワーク非依存 |

**残る実質的な根拠は習熟のみ**（Tauri・OCaml WebView を落としたのと同じ「毎日使うインフラに学習リスクを載せない」基準）。**結論（Vue 3）は変えないが、技術的優位を根拠にしない。**

**性能は選定理由にならない**: ターミナル描画はフレームワークを一切通らない（xterm.js が canvas/WebGL に直接書く）。実測 23 PTY で 254MB。

### やらない

- **状態俯瞰の作り込み** — 差別化「負」（herdr が上位互換）、頻度も低い。doc 13 の最も明確な結論
- **ACP クライアント化** — D1・D2 の撤回を伴う。工数1ヶ月以上
- **UI コンポーネントライブラリ** — PM の画面は専用部品ばかり。「あるから使う」で D7 と同じ drift 経路になる。必要なのはトークン（余白・色・角丸・タイポ）を数個決めることだけ

## リスク管理

### 第二システム症候群

- **リスク**: 「全部作り直す」が「動いていたツールが数週間使えなくなり、そのまま停滞する」
- **歯止め**: 現行版を常用したまま並走。下2層を残すため並走が成立する
- **追加の歯止め**: Phase 0.5（日常価値）を**現行ブランチ**で先に入れる。v2 が長引いても日常の道具は改善される

### WebGL コンテキスト上限

- xterm.js の WebGL アドオンはターミナル1つにつき WebGL コンテキストを1つ消費
- Chromium の上限（16程度）を超えるとコンテキストロスト。23 PTY を抱える PM は踏みうる範囲
- **現状**: `package.json` に WebGL アドオンは入っていない（`@xterm/addon-fit` のみ）。現行が 254MB で収まっているのはこのため
- **対策**: v2 で描画を作り直す際、WebGL を使うかどうかを意識的に決める。使う場合は非アクティブタブを canvas/DOM レンダラに落とすか破棄・再作成
- **未確認**: Electron での実数上限。**実機で確認する**

### xterm.js の既知の問題（乗り換えない判断）

- AI CLI 実行中にスクロールが先頭へ飛ぶ、Kitty キーボードプロトコルのバグ、IME コンポジション
- **乗り換えても解決しない可能性が高い**（AI CLI 特有の描画パターンに起因）。既知の問題として付き合うほうが予測可能
- **監視項目**: xterm.js #5686（libghostty 採用の可能性）/ ghostty-web #141 / xterm.js 7.0 PR #5770

### 監視項目（doc 12）

- **ACP** — エージェント側の採用が広がるかどうかが PM の寄生型アプローチの妥当性を左右する
- **Nimbalyst** — Claude Code と Codex を並べる OSS の visual workspace、Windows 対応。最も近い競合
