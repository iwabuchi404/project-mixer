## 位置づけ

Phase 3 は **v2 の本体**である。機能追加ではなく、**「つぎはぎ」を構造的に直す**フェーズ。

「一体感がない・つぎはぎ」の原因は、各機能が別々のタイミングで別々の判断基準で追加され、**共有された操作の文法がない**ことだった。backlog を1件ずつ潰してもこれは解決しない（その追加をもう10回繰り返す行為になる）。

コマンド層は、その文法を実在させる唯一の手段である。**先に入れておけば、以後の機能追加は自動的に同じ文法に乗る。**

## 現状の問題

操作がイベントハンドラの中に直接書かれており、状態変更がその場で起きている。

```js
tabEl.addEventListener('click', () => {
  openFiles.forEach(f => f.tabEl.classList.remove('active'));
  f.tabEl.classList.add('active');
  activeFilePath = path;              // ← 状態がここで変わる
  editorTextarea.value = f.content;
});
```

この形の帰結:

- **外から呼べない** → MCP から `show_file` を実装できない
- **状態が変数と DOM に散っている** → `get_focus` が「今どのタブか」を集められない
- **新機能を足すたびに別のハンドラの中で状態を変える** → つぎはぎが増える

## Phase 3 後の形

```js
// ① 操作に名前を付けて登録する
commands.register('tab.activate', ({ id }) => {
  state.activeTabId = id;             // ← 状態変更はここだけ
});

// ② UI は呼ぶだけ
tabEl.onclick = () => commands.run('tab.activate', { id });

// ③ エージェントも同じものを呼ぶ
mcp.on('show_file', ({ path, line }) => {
  commands.run('preview.open', { path });
  commands.run('preview.reveal', { line });
});
```

```
MCP (agent) ──┐
キーボード   ──┼→ Command層 → State → 描画
マウス/UI    ──┘
```

**エージェントの操作は特別扱いではなくなり、単に3番目の呼び出し元になる。**

### なぜこれで「つぎはぎ」が直るのか

新機能を足すとき、**必ずコマンドを定義することになる**。定義しようとすると既存の語彙の隣に並べることになり、`tab.activate` / `preview.open` / `terminal.send` が並んでいるところに整合しない名前を置こうとすると**その場で違和感が出る**。

現状は各機能が独立しているためこの摩擦が働かない。コマンド層は、**規律ではなく構造**として統一を保つ。

## 3つの部品

| | 内容 |
| --- | --- |
| **State** | 散らばっている状態（`activeFilePath`、`openFiles`、フォーカス中のターミナル等）を1箇所に集める |
| **Commands** | 操作に名前を付けたレジストリ。状態変更はここを通してのみ行う |
| **Shared View** | MCP サーバ。コマンドを外部に開く薄い層 |

**規律が本体であり、ライブラリの選択ではない。** 「状態変更は必ずコマンド経由」を崩すとコマンド層は飾りになる。

## 段階構成

### 3.0 開発版と常用版の分離（前提・半日）

PM 自身が PM 上で開発されているため、`get_focus` / `show_file` を実装した瞬間に **「エージェントが読んでいるのはどちらの PM の状態か」** が問題になる。

- [ ] electron-builder のインストール版を常用に固定する
- [ ] 開発版は `userData` を分けた別プロファイルで起動する

**Shared View の実装に入る前に片付ける。**

### 3.1 push: 送信時に focus 情報を混ぜる（安い・MCP 不要）

MCP は要求応答であり、**エージェントが呼ばなければ何も起きない**。呼ぶ必要に気づくかはツール説明文次第で、利用率が上がらないリスクが実在する。

一方 PM は送信経路を握っている。**Composer から送るときに focus 情報を本文へ混ぜる**だけなら、MCP なしで確実に届く。

| | 確実性 | 何を解くか |
| --- | --- | --- |
| **push（送信時に混ぜる）** | 高 | 人間が送る瞬間の文脈 |
| pull（`get_focus`） | 低〜中 | ターン中に人間が見ているものが変わったとき |

- [ ] 送信時に、アクティブなファイル・選択範囲・プロジェクトを本文へ付加する
- [ ] 付加するかどうかを切り替えられるようにする（常時オンだと邪魔になる可能性）

**pull の価値を測る基準にもなる。** push で足りるなら `get_focus` の優先度は下がる。

### 3.2 State を1箇所に集約（数日）

**既存コードは動いたまま、状態の置き場所だけを移す。**

- [ ] 「人間の注意状態」を1つのストアに集める
  - アクティブなプロジェクト
  - アクティブなファイルタブとパス
  - 選択範囲・カーソル位置
  - フォーカス中のターミナル
  - scratch の内容
- [ ] DOM から状態を読んでいる箇所を、ストア参照に置き換える
- [ ] ファイルツリーのインデックス（Phase 2.5 で作成）もこのストアの一部として位置づける

**一度に全部を移行しない。** 触ったところから順に移す。

### 3.3 Commands レジストリ（1〜2日）

- [ ] `register(name, handler)` / `run(name, args)` の骨組み
- [ ] 状態変更は必ずコマンド経由、という規約を通す
- [ ] 人間の操作とエージェントの操作が同じ trace に乗るようにする

### 3.4 `show_file` の実装（数日・Phase 3 の本命）

**なぜ `get_focus` ではなく `show_file` が第一歩か**:

- `get_focus` は**読み取り**。状態を集約すればよく、**コマンドを定義しなくても実装できてしまう**
- `show_file` は**書き込み**。外部から UI を動かすため、コマンドが実在しないと実装できない。**コマンド層を本当にテストする**
- エージェント側に呼ぶ動機がある（「ここを見て」と言いたい場面が実在する）ため、利用率の問題が小さい

**必要になるコマンド**（コマンド層の最初の語彙）:

- `preview.open(path)`
- `preview.reveal(line, endLine)`
- `tab.activate(id)`
- `project.setBadge(projectId, kind)`

#### 動作原則

> **「見せる」であって「見させる」ではない。提案するのはエージェント、決めるのは人間。**

| 状況 | 挙動 |
| --- | --- |
| 同じプロジェクトを人間が見ている | プレビューエリアに開き、該当行までスクロール・ハイライト |
| 同じプロジェクトだが人間は別タブ | プレビュータブを作るが**アクティブにしない**（タブにマーク） |
| **別プロジェクト** | タブだけ作り、**PROJECTS 列にバッジ**。プロジェクトは切り替えない |

**やらないこと**: プロジェクト切替、キーボードフォーカスの奪取、ウィンドウの前面化、人間が開いているタブを閉じる／置き換える。

- [ ] タブは既定で使い回す（`new_tab: true` を明示したときだけ増やす）
- [ ] 戻り値で `shown: boolean` を返す（表示されなかったことをエージェントが知れば、代わりにテキストで説明できる。常に `ok` を返すと伝わったと誤認する）
- [ ] `reason` を引数に持ち、タブやバナーに出す（指差しにラベルが付き、翻訳の質が上がる）

**未決**: ハイライトをいつ消すか（次の操作で消す／数秒でフェード／明示的に閉じるまで）。実使用を見て決める。

**副産物**: 別プロジェクトのエージェントが `show_file` を呼ぶと PROJECTS 列にバッジが出る。**「PROJECTS 列がほぼ死んでいる」問題が部分的に解ける。** これは「状態俯瞰はやらない」という決定と矛盾しない ── 稼働状態を推定するのではなく、**エージェントが明示的に人間を呼んだ事実**だけを表示するため。

### 3.5 MCP サーバの基盤

#### セッション同一性（PM 固有の問題）

PM は 5〜10 プロジェクト × 複数ターミナルを同時に抱えるため、**どの文脈の focus を返すかが自明でない**。プロジェクト A のエージェントに B を見ている人間の focus を返せば害になる。VSCode 拡張が抱えなかった問題。

- [ ] ターミナル起動時に `PM_MCP_URL=http://127.0.0.1:PORT/s/<token>` を env で注入する
- [ ] トークンをセッションに紐づけ、認証も兼ねる

PTY を起動するのは PM なので env は確実に注入でき、曖昧さがない。エージェントを信頼しない設計。

**却下した案**: 引数で `project_path` を要求（エージェントが正しい値を渡す前提に依存）、プロジェクトごとにサーバを立てる（管理が煩雑）。

#### トランスポート

ローカル HTTP/SSE（127.0.0.1 バインド）。**stdio は使えない** ── stdio はエージェントが PM を子プロセスとして起動する形になるが、実際は逆（PM がエージェントを起動している）ため成立しない。

#### 設定の注入はプロジェクト内ファイルを書き換えない

エージェントに MCP サーバを教えるには `.mcp.json` か `claude mcp add` が必要になる。**これは `.claude/settings.json` 自動生成と同じ問題**。`.mcp.json` をコミットして共有しているプロジェクトでは PM が上書きして差分を作る。

- [ ] 起動時フラグ（`--mcp-config` 相当）かユーザースコープの設定に寄せる
- [ ] プロジェクト内のファイルを書き換えない

#### セキュリティ

ローカル HTTP は同一マシンの任意のプロセスから叩ける。トークンで塞ぐが、**トークンをログや `env` 出力に露出させない**（エージェントが `env` を実行すると見えてしまう）。

### Shared View のツールは4つに絞る

MCP ツールはエージェントのコンテキストとツール選択を圧迫する。PM が10個並べると、エージェント本来のツール（Read / Edit / Bash）との選択が難しくなり**エージェントの性能が落ちる**。

**3〜4個に絞るのは妥協ではなく設計。**

| ツール | 状態 |
| --- | --- |
| `show_file` | **Phase 3 で実装** |
| `get_focus` | push の後 |
| `show_browser` | Phase 4 |
| `show_diff` | 保留 |

**却下したもの**: `ask_user`（TUI が既に持つ）、`notify`（フックと重複）、`create_terminal` / `run_command`（実行）、`switch_project` / `close_tab`（エージェント都合の操作）、`get_project_list`（他プロジェクトの覗き見）、`show_preview` / `show_image`（`show_file` が拡張子で判定するため不要）、`draw_diagram` 等の出力系（ファイル + `show_file` で足りる）。

## 未解決の判断（Phase 3 期間中に決める）

### L1（プレビューをメインエリアへ）

Phase 2.5 で L4（畳み込み）を実施済み。数日の実使用で判断する。

**判断基準**:

1. **畳む動機がプレビューを読むためなら → L1 が必要**。畳まないと読めないということは既定レイアウトが破綻している
2. **HTML プレビューでモバイルのブレークポイントが出るなら → L1 が必要**。デスクトップ表示の確認には概ね 800px 以上が要る
3. 畳まずに使えていて上記が起きないなら → 右カラムのままでよい

2 は主観が入らないため**最も信頼できる判定材料**。

**Phase 3 への影響**: `preview.open` がどこに開くかが変わるため、**3.4 の前に決めるほうが安全**。後から直すとコマンドの意味が変わる。

## 実装上の注意

### `<webview>` を維持する

Phase 4 プランで WebContentsView への移行が想定されていたが、**移行コストを過小評価していた。この方針は取り消す。**

| | DOM 要素か | プロセス | レイアウト |
| --- | --- | --- | --- |
| `iframe` | はい | 基本同じ | CSS が効く |
| **`<webview>`** | **はい** | **別** | **CSS が効く** |
| `WebContentsView` | **いいえ** | 別 | **座標を手で管理** |

**WebContentsView は DOM ツリーの外にいる。** 位置・サイズ・重なり順はすべて main プロセスからの `setBounds` で管理される。帰結:

1. **常に一番上に浮く。** PM のタブバー・ドロップダウンは、ビューと重なる位置にあると隠れる
2. **CSS が効かない。** `display:none` で隠せず、`z-index` も効かない
3. **座標を手で計算し続ける。** リサイズ・畳み込み・ドラッグのたびに矩形を再計算。**A1 と同種の問題が1つ増える**

`<webview>` は **DOM 要素でありながら別プロセス**。`file://` を読め、CSP の影響を受けにくく、`partition` でセッションを分離でき、preload も使える。**プレビュー（`file://` + 相対パス解決）には `iframe` では代替できない。**

「非推奨」の警告は数年前から存在し削除されていない。「明日消える」ではなく「積極的には改善されない」状態。

**既知の癖**:

- 非同期。生成直後にメソッドを呼んでも効かない（`dom-ready` を待つ）
- **`display:none` で隠すとサイズが 0 になり、再表示時に描画されないことがある。A1/A2 と同型の問題**
- 生成コストが高い（1つにつきプロセス1つ）。**タブごとに増やさず、1つ持って `src` を差し替える**

### タブ設計

ターミナルタブ（長命）とプレビュー / ファイルタブ（使い捨て）は**寿命が違う**。同じタブバーに混在させると**プレビューを閉じるつもりでターミナルを閉じる事故**が起きる。対策は以下のいずれか1つで足りる。

- アイコンで区別する
- プレビュータブをバーの右寄せにする
- ターミナルタブを閉じるときだけ確認を出す

## 移行戦略（最大のリスクへの歯止め）

**リスク: 第二システム症候群。** 「0ベースで考える」が「全部作り直す」になり、動いていたツールが数週間使えなくなり、そのまま停滞する。

**歯止め**:

> **現行版を常用したまま、新アーキテクチャを別ブランチで進める。新版が現行版の日常作業を代替できた日に切り替える。**

コマンド層の新設は PTY 層とランタイムを残すため、この並走が成立する。**既存コードとコマンド層は共存できる。** 全部を書き直すのではなく、新しい操作から順に乗せていく。
