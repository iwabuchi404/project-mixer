## 調査結果: kamox は何を既に提供しているか

Phase 3 の設計は「kamox 側の対応範囲」に依存する。`D:\work\kamox` を確認した結果、**当初の想定より遥かに多くが既にある**。

### HTTP API（`http://localhost:<port>`、既定 3000）

| エンドポイント | 返すもの |
| --- | --- |
| `GET /status` | `serverRunning`, `environment`, `projectName`, `buildCount`, `lastBuildTime`, `isRebuilding`, `features` |
| `POST /check-ui` | `screenshot`（**絶対パス**）, `dom`, `logs`, `errors`, `performance` |
| `GET /screenshots/:filename` | **PNG バイナリ**（`/check-ui` が撮ったものと同一） |
| `GET /logs` | `runtime[]` と `pages[]` のログ |
| `POST /playwright/*` | mouse / keyboard / element / wait / reload / evaluate |
| `POST /rebuild` | ビルド + リロード |

### ダッシュボード（`GET /`）

**kamox は既に HTML ダッシュボードを配信している**（`packages/core/src/DevServerAPI.ts`）。内容はステータスバッジ、直近 100 件のログ、Check UI ボタン（押すとスクショと DOM をモーダル表示）、Electron なら Restart App。

### 重要な確認事項

- **kamox にライブストリーミング機能は無い。** screencast も CDP 中継も持たない。**リクエスト/レスポンス型のスクショ**が現状の全て
- **kamox は意図的に MCP を持たない**（「curl が叩ければ十分」という設計判断）。PM 側は HTTP を叩くだけでよい
- ポートは `-p, --port` と `kamox.config.json` の両方で指定できる
- PM 自身のリポジトリにも `kamox.config.json`（`mode: electron`, `port: 3000`）が既にある

## 設計の方向転換: ライブ埋め込みから始めない

`docs/IMPLEMENTATION_PLAN_v2.md` の Phase 3 は、経路1（CDP screencast）と経路2（PM が WebContentsView を出しエージェントが CDP 接続）の二択で書かれている。**どちらも「ライブに動くブラウザ面を PM 内に持つ」前提**である。

しかし調査の結果、以下が判明した。

1. **kamox はライブ映像を出さない。** 経路1 は kamox ではなく Playwright のブラウザへ PM が直接 CDP 接続することを意味し、**D15（PM は Playwright を管理しない）の境界に触れる**
2. **経路2 は PM が CDP エンドポイントを開くことを要求する**（未解決のセキュリティ検討事項として既に記録済み）
3. **実際のレビュー経路は「マークダウン要約 + 動作確認」**であり、**動画である必要は無い**。スクリーンショットとログで足りる可能性が高い

> **結論**: ライブ表示を最初の実装対象にしない。**静止画 + ログから始め、実使用で不足を測ってからライブ表示の要否を判断する。**
> これは第二システム症候群への歯止め（`IMPLEMENTATION_PLAN_v2.md` リスク管理）と、D15 の「見えるようにするだけ」の両方に沿う。

## 段階構成

### 3.1 kamox 検出とダッシュボード表示（最小実装）

**狙い**: 最小の工数で「動作が見える」状態を作り、同時に **Phase 3 の本命である WebContentsView の矩形追従機構を実地で検証する**。

kamox のダッシュボードは既に必要な情報（ステータス・ログ・Check UI）を持つ HTML ページなので、**PM 側の描画をゼロにできる**。

- [ ] アクティブプロジェクトの `kamox.config.json` を読み、ポートを得る
- [ ] `GET /status` を叩いて kamox が起動しているか判定する（起動していなければ何も出さない）
- [ ] WebContentsView でダッシュボード（`http://localhost:<port>/`）を表示する
- [ ] `window.__pmGetPaneRect(paneName)`（Phase 2 で用意済み、`renderer.js:2609`）から矩形を取り、main 側で WebContentsView の bounds に反映する
- [ ] レイアウト変更・スプリッタ操作・L4 の畳み込み・タブ切替のたびに矩形を送り直す
- [ ] プロジェクト切替で対象ポートを切り替える

**この段階で分かること**: 矩形追従が実用に耐えるか。ダッシュボードで足りるのか、PM 側で情報を選別する必要があるのか。

### 3.2 PM 側での表示（3.1 で不足が確認された場合のみ）

ダッシュボードは kamox 単体で使う前提の画面なので、PM の中に置くと情報の粒度が合わない可能性がある。その場合のみ実施する。

- [ ] `GET /screenshots/:filename` の画像を PM のプレビュー機構で表示する（Phase 2 のプレビュー基盤に載せる）
- [ ] `GET /logs` のエラーだけを抜き出して表示する
- [ ] `GET /status` の `isRebuilding` / `lastBuildTime` をステータスバーに出す
- [ ] スクショの更新契機を決める（ポーリング / エージェントのフック / 手動更新）

> **注意**: ここは「kamox のダッシュボードを PM 内に作り直す」作業になりやすい。**3.1 を使って具体的な不足を1つ以上挙げられない限り着手しない。**

### 3.3 ライブ表示（要否を判断してから）

3.1 / 3.2 を数日使い、**「静止画では判断できなかった場面」が実際に出たときだけ**検討する。

判断が必要な事項:

- 経路1（PM が Playwright のブラウザへ CDP 接続して screencast を受ける）は D15 の境界に触れる。**D15 を改訂するかどうかの判断を伴う**
- 経路2（PM が remote debugging を開く）は**セキュリティ検討が前提**。localhost のみ・トークン必須などの方針を先に決める
- そもそも kamox 側にライブ機能を足す選択肢もある（kamox は自分のプロジェクト）。**その場合は kamox 側の設計判断として別途記録する**

## 未解決の設計判断（3.1 着手前に決める）

### 1. kamox サーバは誰が起動するか

D15（PM は Playwright を起動・管理しない）に素直に従うなら **エージェントが起動し、PM は検出するだけ**。

- PM が起動する形にすると、PM がビルドツールのライフサイクルを持つことになり、D15 の境界が崩れる
- 一方、毎回エージェントに起動させるのは摩擦になる可能性がある

**暫定方針**: 検出のみ。起動は行わない。摩擦が実測されたら再検討する。

### 2. ポート衝突（5〜8 プロジェクト同時運用）

kamox の既定ポートは **3000 固定**。PM は 5〜8 プロジェクトを同時に開く前提なので、**複数プロジェクトで kamox を動かすと必ず衝突する**。

これは PM が Phase 0 で自分自身に対して解いた問題と同型（固定ポート → プロファイル別 + ポートファイルによる discovery）。

選択肢:

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 各プロジェクトの `kamox.config.json` に別ポートを書く運用にする | PM 側の実装ゼロ。設定漏れは `GET /status` の失敗として現れる |
| B | PM がポート走査で見つける | 無認証の localhost サーバを総当たりすることになり筋が悪い |
| C | kamox 側にポートファイル出力を足す | kamox の変更が必要。PM の Phase 0 と同じ機構になり一貫する |

**暫定方針**: **A で始める。** 実運用で設定漏れが頻発したら C を kamox 側の課題として起票する。

### 3. 表示場所

L1 の判断結果に従う。L1 が「メインエリアへ」なら動作表示もメインエリアが自然。右プレビュー列のままなら、**動作表示とファイルプレビューがタブとして同居する**設計になる。

> Phase 2.5 の「タブ設計上の注意」がここでも効く。**ターミナルタブ（長命）とプレビュータブ（使い捨て）の混在事故**と同じ問題が、動作表示タブでも起きる。

### 4. 接続先の制限（セキュリティ）

kamox は **localhost の無認証 HTTP** である。PM が任意のポートに接続する作りにはしない。

- 接続先は **アクティブプロジェクトの `kamox.config.json` に書かれたポート**に限定する
- `GET /status` の `projectName` を照合し、想定と違うサーバなら表示しない

- [ ] エージェントが kamox 経由で操作した結果が PM の画面内で見えること
