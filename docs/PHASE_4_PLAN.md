## L1 判断は確定済み（案B）

Phase 2.5 から持ち越していた L1 は **案B で決着した**。これにより Phase 2.5 の必須範囲は終了する。

### 判断の根拠となった実測

全幅 1563px での領域占有率:

| 領域 | 幅 | 占有 |
| --- | --- | --- |
| PROJECTS | ~200px | 13% |
| ツリー | ~245px | 16% |
| **ターミナル** | ~580px × 高さ55% | **約24%** |
| scratch | ~580px × 高さ30% | 13%（空でも） |
| プレビュー | ~535px | 35% |

**エージェントとの会話が起きる場所が画面の 1/4 しかなく、最大面積を占めていたのは読んでいない README だった。**

### 原因: 常設と随時が同じ扱いになっていた

| | 実際の必要性 | 現状 |
| --- | --- | --- |
| ターミナル | **常時** | 24% |
| ツリー | 投入時 | 常設 16% |
| プロジェクト | 切替時 | 常設 13% |
| scratch | 組み立て時 | 常設 13%（空でも） |
| プレビュー | 確認時 | 常設 35% |

**5領域すべてが常設で、常時必要なのは1つだけ。** 「狭く感じる」の正体は個々の領域が狭いことではなく、**常設すべきでないものが常設されていること**だった。

### L4 の実験結果は当初の解釈が逆だった

畳むとターミナルは 580px → 985px、占有率 24% → **41%**。当初「幅が全部ターミナルに行ったので実験にならない」と判断したが、**飢えていた主役に幅が回っただけで、正しい挙動だった**。

プレビューは 535px のまま。ここから L1 の答えが出る。

| 中身 | 535px で足りるか |
| --- | --- |
| Markdown | 足りる |
| 画像 | 足りる |
| **ブラウザ（dev server）** | **足りない**（モバイル幅のブレークポイントになる） |

**中身によって答えが違う**ため、「右に固定」も「中央に固定」も正解ではない。**必要なときに中央を使える形**が要る。

## 目標レイアウト（案B）

```
[サイドバー]  [ メインタブ: term | term | README | localhost ]
 プロジェクト  ┌──────────────────────────────────────────┐
 ツリー        │                                          │
 （畳める）    │                                          │
              ├──────────────────────────────────────────┤
              │ scratch（薄く常駐、フォーカスで伸びる）    │
```

- ターミナルもプレビューもブラウザも**同じ中央タブ**に入る
- 見たいものが常に最大幅を得る
- 常設は「ターミナル or いま見ているもの」の1つだけ
- VSCode と同じ構造（「慣れた UI」方針に合致）

### 却下した案

- **案A（現状維持 + 随時のものを縮める）**: 変更は最小だが、5領域常設という構造が残る
- **案C（B + プロジェクトとツリーを1列に統合）**: さらに ~200px 空くが、**プロジェクト一覧の常時可視性を失う**。横断の俯瞰は PM の中核価値なので採らない

### D12 の差し替え

D12（レイアウトは翻訳の方向で決める）を **「注意で決める」に差し替える**。

| 場所 | 役割 |
| --- | --- |
| 左（細い・畳める） | **常に参照するもの**（周辺視野）— プロジェクト、ツリー |
| 中央（広い・タブ） | **いま見ているもの**（中心視野）— ターミナル / プレビュー / ブラウザ |
| 中央下 | **いま書いているもの** — scratch |

方向は**データの流れ**の性質であって、**注意**の性質ではなかった。人間はある瞬間に1つしか見ておらず、プレビューとターミナルは**時間的に排他**である。排他的なものは場所を共有すべきで、分割すべきではない。

## デザイントークン（確定値）

### 色 — 彩度調整では解けなかった

当初 `--attn`（琥珀）と `--act`（青）を置いたが**喧嘩した**。彩度を落として対処したが**誤り**。

> **琥珀（35°）と青（210°）はほぼ補色。補色は「どちらも引かない」関係なので、彩度を揃えると互いに同じ強さで主張し合う。** 明度・彩度の調整では構造的に解けず、**色相をずらすか色を使うのをやめるかの二択**になる。

**採用: スレートティール**（色は残すが補色関係を外す）。

| トークン | 値 | 用途 |
| --- | --- | --- |
| `--attn` | `#c08b4d` | 人間の介入が必要（入力待ち・エージェント操作） |
| `--act` | `#4d8480` | 主要動作（送信・確定） |
| `--err` | `#b56b66` | エラー |
| `--ok` | `#5f9278` | 差分の追加 |
| `--g-0`〜`--g-6` | `#16181c` → `#f0f2f5` | 単一色相（220°）6段階 |

`--act` は琥珀との距離が 141° で補色を外れ、冷たい色として「構造的な UI 要素」に読まれる。**ボタンの文字色は暗く**（`#0d1412`）する — ティールは中明度のため白文字ではコントラストが不足する。

**1色 = 1つの意味。** オレンジは「人間の介入が必要」専用にする。理由は美観ではなく機能で、5〜10 プロジェクトを走査するとき **色が出ている＝行動が要る**と1対1で対応していれば目が勝手に見つける。**アクティブ状態や選択項目に色を使うと常に色が見えている状態になり、`●` の効果が消える。**

### 境界 — 明度差で表し、線は引かない

**ペイン間には線を引かない。** 地（`--g-0`）の上に面（`--g-1`）を 1px の隙間を空けて並べると、**隙間そのものが境界になる**。

```css
.app  { display: flex; gap: 1px; background: var(--g-0); }
.pane { background: var(--g-1); }
```

| レイヤー | 境界の表し方 | 値 |
| --- | --- | --- |
| L1 ペイン間 | 地の隙間 1px | `gap:1px` / `--g-0` |
| L2 ペイン内 | 面の明度差のみ | `--g-1` / `--g-2` |
| L3 浮いた面 | 影のみ | `--shadow` |

**`border` を書いてよい3つの例外**:

1. 入力できる領域の輪郭（「打てる」ことを示す機能）
2. 意味的な区切り 1本（メニュー内のグループ分け）
3. フォーカスリング（キーボード操作時のみ）

> **この3つ以外で `border` を書いたら規則違反。** 判定が機械的なので実装中に迷わない。

**やらないこと**: 面 + 線の併用（二重に境界を主張し階層が読めなくなる）／色付きの枠（`attn` を枠に使うと `●` が埋もれる）／浮いていない面に影（**影が付いていること自体が「一時的に浮いている」という情報**なので、常設の面に付けると情報が消える）。

### 影・トランジション・アイコンは「必要」

当初「作業道具に装飾は要らない」として除外したが**誤り**。それぞれ具体的な仕事がある。

- **影** — ドロップダウンが背後のターミナルに溶けている。**影は装飾ではなく深度の手がかり**。1段階だけ、浮いているもの（Menu / Toast）に限る
- **トランジション** — サイドバーを畳むとレイアウトが瞬間移動し、「畳んだ」のか「表示が壊れた」のか区別できない。100〜150ms、1種類。**ターミナル幅のアニメーションは避ける**（1フレームごとに `fit()` + SIGWINCH が走り TUI が全画面再描画する）
- **アイコン** — タブ種別の判別。**タブ混在事故の最も安い対策**

> **修正した原則**: 「装飾を足さない」ではなく **「それぞれが状態を説明しているか」**。説明していないものだけを落とす。

| | 方針 |
| --- | --- |
| グレー | 1色相で 5〜6 段階。他の色相のグレーを混ぜない |
| 余白 | 4px 基準、5段階まで（4/8/12/16/24） |
| フォントサイズ | 3段階まで |

## デザインシステムの範囲

**フルセットは作らない。** デザインシステムは本来チーム間のコミュニケーション装置であり、1人のプロジェクトではその価値を回収できない。**Storybook もドキュメントも不要。**

| | 中身 |
| --- | --- |
| **トークン** | CSS 変数1ファイル |
| **プリミティブ** | Tab / ListRow / Button / Menu / PaneHeader / Splitter / Badge / Input / Toast の**9個のみ** |

**PM が容れ物である以上、部品はクロームだけ。** 中身（ターミナル出力、プレビュー、差分）はすべてよそのものなので、コンポーネントの種類は増えない。9個で打ち止めになるはず。

- **Tab は1コンポーネントに統一**し、種別はアイコンだけで表す
- **アクティブ状態は明度差で表す**（「状態は明度、意味は色」。境界の扱いとも揃う）

## メッセージ表示

### 原則

> **人間が起こしたことは消えてよい。エージェントが起こしたことは消えてはいけない。**

「コピーしました」（本人は知っている）と「エージェントが PM を操作した」（**知らないかもしれない**）は性質が正反対。

**トーストはエージェントの操作には向かない。** 5〜10 プロジェクトを抱え、別のプロジェクトを見ている最中に消えるメッセージが出ても、**見ていないので存在しなかったのと同じ**。

| | 何に使うか | 挙動 |
| --- | --- | --- |
| **Toast** | コピー完了など人間起点 | 1.5秒で自動消滅。**操作した場所の近く**に出す（画面隅だと視線が飛ぶ） |
| **Badge** | エージェントの操作、入力待ち | **見るまで消えない**。PROJECTS 列とタブに付く。`--attn` |
| **Error** | 送信失敗、接続断 | 自動消滅しない。閉じるまで残る |

Badge は D13-3 で既に決めていたものと同一。**Phase 3 で実装した `show_file` のバッジがそのまま「エージェントが操作した」の表示になる。** 新しい仕組みではなく既存設計に乗る。

### Toast で出すもの

**判定基準**: **やったのに、画面が何も変わらないもの。**

**A. 結果が画面に出ない操作**

| メッセージ | 理由 |
| --- | --- |
| パスをコピーしました `src/App.vue` | クリップボードは見えない |
| スクショを保存しました `tmp/shot-03.png` | パスは挿入されるが**保存先**は見えない |
| 200行を追加しました | 何行入ったか分からない |
| context を添付: App.vue L12-40 | push（Phase 3.1）で何が付いたか。チェックボックスだけでは中身が見えない |

**B. 取り消せる操作 — Toast は undo の置き場所**

D8 で「送信後クリア、直前1件は復元可」と決めているが、**その復元手段を人間が知る経路がない。**

- 送信しました ｜ **元に戻す**
- タブを閉じました ｜ **元に戻す**
- プロジェクトを削除しました ｜ **元に戻す**

**Toast がないと、可逆であること自体が発見されない。** 確認ダイアログを出すより、実行してから取り消せるほうが速い。

**C. 意図と違う結果になった操作（PM 固有・最も見落とされやすい）**

| メッセージ | 背景 |
| --- | --- |
| **バイナリのため OS の既定アプリで開きました** | A4 の実装挙動。PM 側は何も表示されないので「開かなかった」に見える |
| **bracketed paste 非対応のため行単位で送信しました** | フォールバックが起きたことが分からない。**送信結果の正しさに関わる** |
| **プロジェクト外のファイルのため絶対パスで挿入しました** | 相対パスを期待していると食い違う |

**C は「失敗ではないが期待と違う」領域。** エラーではないので Error にできず、黙っていると原因不明の混乱になる。

**D. 時間がかかった操作の完了** — ファイルインデックスの再構築など。ただし**ステータスバーのほうが適切な可能性**がある。

### Toast で出さないもの

送信（`→ devin` の表示が変われば不要）／タブ切替・プロジェクト切替／ツリーからの選択（scratch に見える）／D&D での挿入（ターミナルに見える）。

**クリックしたら反応する、は UI 自体が示すべき。** 文字で言われると邪魔になる。

### 規律: 毎回出るものは消す

**同じ操作のたびに必ず出るトーストは数日で見えなくなる。** 一度「トーストは無視するもの」になると、**C が届かなくなる** — そちらが本当に読ませたいものなので損失が大きい。

> **その操作を100回やって、100回とも同じことが起きるなら、トーストは要らない。**

この基準で A からもいくつか落ちる。「ファイルを保存しました」は毎回同じなのでタブのマーク（`*` が消える）で十分。**A の中でも結果が変動するもの（保存先、行数、添付内容）が残る。**

### Toast の見た目

**左ボーダー方式（`border-left: 3px solid`）は撤回。** Bootstrap の alert 以来のパターンだが、**意味を色面で運ぶという考え方自体が「器は色を持たない」方針と矛盾する。**

**採用: 統一サーフェス + 先頭グリフ。** 面はすべて同じで、意味を運ぶのは先頭グリフの色だけ。色の総面積が 14×14px に収まるため `●` の存在感を奪わない。**undo は下線付きの中立色ボタン**にする（`--act` を使うと主要動作と混同する）。

**不採用**: ステータスライン型（ペイン下端に1行）— ターミナルの隣にある道具としては自然だが、**undo の存在に気づきにくい**。取り消せる操作が主要用途なので不利。

### 実装上の注意

- **まとめる**。エージェントが `show_file` を10回呼んでもトーストが10枚出てはいけない。同種のものは差し替えるか件数で表示する
- **自分の操作に出しすぎない**。「起きたか分からない操作」だけに出す

## 実装上の注意（PM 固有の再燃リスク）

案B は**中央タブの表示切替を増やす**ため、Phase 2.5 で潰した問題が再燃しうる。

1. **A1（0 寸法での `fit()`）** — タブ切替でターミナルが `display:none` になる頻度が上がる。`resizeTerminalToContainer()` の 0 寸法ガードと、`requestAnimationFrame` 後の測定がタブ化後も効いているか確認する
2. **A2（pinned-to-bottom）** — タブを離れて戻ったときの追従状態の維持を回帰確認する
3. **`<webview>` の癖** — ブラウザタブを中央タブに入れると直撃する。**`display:none` で隠すとサイズが 0 になり再表示時に描画されないことがある**（A1/A2 と同型）。加えて生成コストが高いため、**タブごとに `<webview>` を増やさず、1つ持って `src` を差し替える**
4. **トランジションをターミナル幅に掛けない**（前述）

> **`<webview>` は維持する。** WebContentsView への移行方針は「移行コストを過小評価していた」として取り消し済み（doc 12 の訂正）。WebContentsView は DOM ツリーの外にいるため、CSS も z-index も効かず、矩形を手で管理し続けることになる。

超えている分が「つぎはぎ」の実体。**直す前と後で数えれば進捗が測れる。**

### 実機で確認する項目

- **色が3つになるぶん `●` の相対的な強さが落ちる。** 5〜10 プロジェクトを並べて `●` が拾えるか
  - **拾えない場合は `attn` を強めず、周囲（`--g-4` など）を下げる。** 目立ちは絶対値ではなく相対値であり、`attn` を上げると `--act` との緊張が戻る
- 案B のタブ切替でターミナルが壊れないこと（上記の再燃リスク1・2）
- サイドバーの畳み込みトランジションが「壊れた」ではなく「畳んだ」と読めること
