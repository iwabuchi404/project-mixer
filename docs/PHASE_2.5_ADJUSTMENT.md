### P0: 安定性（作業が止まるため最優先）

| | 項目 | 分類 |

**A1とA2は同じターミナル表示経路に関係するため、診断はまとめて行う。** ただし、同一原因とは決め打ちしない。

#### 現状確認: 非表示ターミナルへの一斉 `fit()` は行っていない

タブ機構により、非アクティブなターミナルは `display:none` で隠されている（doc 12「v2アーキテクチャ」訂正2）。

- 現在の `handleResize()` は `activeTabId` の1端末だけを対象にしている
- リサイズは50msデバウンス済みで、非表示端末へ一斉に `fit()` を投げてはいない
- 一方、タブ再表示直後に同期的に `fit()` している点、0寸法を拒否するガードがない点、追従状態を管理していない点は調査対象

**診断・対処方針**:

- [ ] ウィンドウ変更、スプリッタ、プロジェクト切替、タブ切替、L4開閉の各経路で再現条件を分ける
- [ ] `tabId`、表示状態、コンテナpx、計算したcols/rowsを記録し、0または不正値をPTYへ渡さない
- [x] 表示切替時はレイアウト確定後に `fit()` → 値が変わった場合だけ `pty.resize()` の順で実行する
- [x] 非表示のターミナルには `fit()` も `resize()` も投げない
- [x] ResizeObserver の循環と、同じcols/rowsの重複送信を防ぐ

#### A2 の別要因: 上流の既知バグの可能性

xterm.js系のターミナルでは **AI CLIツール（Claude Code / Codex）実行中にスクロール位置が飛ぶ**報告がある（[2code #144](https://github.com/AkaraChen/2code/issues/144)）。関連する[xterm.js PR #5770](https://github.com/xtermjs/xterm.js/pull/5770)はmasterへマージ済みだが、Project Mixerが使用中の5.5.0には含まれず、7.0リリース待ち。

- [ ] 自前コードを疑う前に、**素の xterm.js でも再現するかを切り分ける**。上流のバグなら自分で直そうとしない

#### A2の確定動作: pinned-to-bottom

- [x] 出力前に最下部にいた場合だけ、新しい出力後も最下部を追従する
- [x] ユーザーが過去ログへスクロールしている場合は、その位置を維持する
- [x] タブを切り替えて戻った後も、追従中かどうかを維持する
- [x] リサイズだけを理由に無条件で `scrollToBottom()` しない

#### A3の確定動作

| ドロップ先 | 動作 |
|---|---|
| 右プレビュー / メイン領域 | ファイルを読み取り専用で開く |
| scratch | 絶対パスを追記する |
| ターミナル | 使用中シェル向けに引用したパスを挿入する。Enterは送らない |
| ファイルツリー | 何もしない |

- OS Explorerとアプリ内ファイルツリーで同じ規則を使う
- プロジェクト外のファイルも閲覧・パス挿入を許可するが、コピーや移動はしない
- Electron 31では非推奨の `File.path` に依存せず、preload経由で `webUtils.getPathForFile()` を使う

#### A4とL1の関係

A4 は「下部scratchはファイルを閲覧・編集する場所ではない」という主張であり、閲覧と編集の行き先を分ける。

- ダブルクリック: 右プレビューで読み取り専用表示
- 対象: 画像、HTML、Markdown、コード、通常テキスト
- コンテキストメニューの「編集」: 中央メイン領域（右プレビューの左側）で編集
- 未対応バイナリ: OSの既定アプリで開く
- `get_focus`: 右プレビューまたは中央編集面の対象ファイルを現在の注目対象として返す
- ファイル編集のために下部scratchを開かない

中央メイン領域で編集面を表示している間もターミナルPTYは終了させない。ターミナル面と編集面の具体的な切替UIは、A4の実装設計で現在のタブ分離を壊さない形にする。

右プレビュー列に出すと、**すでに「狭い」と判断された場所に主要な閲覧対象を置くことになる**。そのためA4を暫定実装した後、L4適用下でL1（プレビューをメインエリアへ）の必要性を評価する。

L1はA4の着手前には決めず、L4とA4を数日使用した後に判断する。

## タブ種別ごとのメニュー（A5）

現在はターミナル、scratch / editor、previewでタブバーが分離されている。共通メニューを無理に作らず、タブ種別ごとに有効な操作だけを表示する。

- ターミナル: 表示名変更、cwdコピー、閉じる
- preview / 編集ファイル: パスコピー、OSで開く、閉じる
- scratch: 表示名変更、閉じる
- 実ファイルのrenameはPhase 2.5に含めない

## 判断（2026-08）: 閲覧は右プレビュー、編集は中央メインへ。L1はL4の効果を見てから決める

**決定**: A4は、閲覧を当面 **右プレビューエリア**、編集を **中央メイン領域（右プレビューの左側）** に出す。L4（プロジェクト列・ツリーの畳み込み）で幅がどう変わるかを見てから、L1を判断する。

**この順序の利点**: L4 は使える幅を変えるため、「右カラムは狭すぎるか」という問いを **新しい条件下で再テストできる**。L1 を先に決めてしまうより情報が増える。

### 実装順への影響

L4 が**評価の前提条件**になったため、P2 の摩擦解消ではなく **評価の一部** として順序が上がる。

> **A1・A2（安定性） → L4 → A4 → 数日使用 → L1 判断**

### A1 は L4 の前提（重要）

**サイドバーを畳む操作はターミナルのリサイズを引き起こす。** A1（リサイズ不安定）が残ったまま L4 を入れると、畳むたびにターミナルが壊れる。

その結果、**A1 のせいで起きた不具合を L4 の欠陥と誤認する**危険がある。A1 を先に潰す。

### 実装上の分岐点: 空いた幅の行き先

畳んで空いた幅を **どこが吸収するか** で実験の意味が変わる。

- 全部ターミナルが吸収する → プレビューは狭いままで、**実験から何も分からない**
- プレビューが吸収する → 意図した比較になる

L4の確定動作は以下とする。

- `Ctrl+B`でPROJECTS列とファイルツリーをまとめて開閉する
- 各列のヘッダーに個別の折り畳みボタンを置く
- 片方または両方を畳んだ場合、画面左端に細い復元バーを表示し、列ごとのボタンから戻せるようにする
- 復元時は以前の幅を使う
- 開閉状態と各列の幅を再起動後も保存する
- 畳んだだけではプレビュー幅を自動変更しない。既存スプリッタでユーザーが配分する

L1の評価時はプレビューを概ね800pxまで手動で広げ、右カラムで実用になるか確認する。

### L1 の判断基準（先に決めておく）

「なんとなく良い / 悪い」で判断すると結論が出ないため、基準を先に置く。

1. **畳む動機がプレビューを読むためなら → L1 が必要**。畳まないと読めないということは、既定のレイアウトが破綻している
2. **HTML プレビューでモバイルのブレークポイントが出るなら → L1 が必要**。デスクトップ表示の確認には概ね 800px 以上が要り、畳んでもその幅に届かないなら右カラムでは原理的に不可能
3. 畳まずに使えていて、上記が起きないなら → 右カラムのままでよい

2 は主観が入らないので、**最も信頼できる判定材料**。

### L1 の結論（2026-08-13）: 案B で確定 — Phase 2.5 終了

**基準2 で決着した。** プレビュー幅は畳んでも 535px のままで、Markdown と画像には足りるがブラウザ（dev server）には足りない。**中身によって答えが違う**ため、「右に固定」も「中央に固定」も正解ではなく、**必要なときに中央を使える形**＝メインエリアのタブ化（案B）を採る。

L4 の実験結果の解釈も訂正された。畳むとターミナルは 24% → 41% になるが、これは「幅が全部ターミナルに行って実験にならなかった」のではなく、**飢えていた主役に幅が回った正しい挙動**だった。

> **実装は Phase 4 で行う。** 詳細・根拠・レイアウト案は [`PHASE_4_PLAN.md`](./PHASE_4_PLAN.md) を参照。
> これにより **Phase 2.5 の必須範囲は終了**（A1・A2・A3・A4・L4 完了 + L1 判断の記録）。
